# UX acceptance — bounded first release

Reviewed on 2026-11-01 against the working source labeled **1.4.4 / build 11** and the criteria in [ux-audit.md](ux-audit.md). This review inspected source and regression-test coverage. It did not operate the native app, rerun the complete quality gate, or change release readiness.

**Disposition:** the bounded reliability UX contract below is accepted by source review. No new source blocker was found in that contract. Native interaction acceptance remains unperformed, final quality verification is pending, and this document does not approve publication or claim that all UX issues are resolved.

## Test evidence and limits

The earlier runs in `/tmp/glimpse-app-green.log` and `/tmp/glimpse-core-green.log` reported **54 app tests in 9 suites** and **62 core tests in 5 suites** before the final About corrections. The subsequently inspected `/tmp/glimpse-app-final.log` reports **57 app tests in 9 suites** and `TEST SUCCEEDED`, with results at `build/validation/app-validation-final-4.xcresult`. This latest app run includes the explicit save destination and partial-report corrections. The complete final quality and artifact gates remain separate requirements.

The inspected regressions address login success readback, nonenabled system statuses, failure recovery, rapid requests, external refresh, selected-day queries, DST day boundaries, stale requests, revocation, fetch failure/retry, and duplicate permission requests. Diagnostic tests cover large output, timeout, nonzero exit, an unavailable executable, saving metadata/logs at the supplied destination, retaining a useful report when collection fails, and reporting destination write failure. These tests use temporary file destinations; they do not validate a native SavePanel or Powerbox grant. Keyboard tests exercise a pure routing decision; they do not deliver live AppKit events, inspect VoiceOver, or establish monitor lifetime.

## Native evidence is limited

[qa-live.md](qa-live.md) records that an isolated accessory app launched and exposed an enabled menu extra. Thirteen closed-panel samples spanning **60.47 seconds** showed sampled `ps` CPU median and maximum of **0.0%**, with cumulative CPU unchanged at reporting precision. This supports the absence of a sustained closed-panel loop during that minute only.

The QA copy retained **1.4.3 / build 10**. Source bookkeeping later became 1.4.4 / build 11, and the retained Finder/export-again About correction and standard save-dialog correction were absent from the tested copy. This native observation must not be described as final 1.4.4/build 11 validation.

CUA could not select the isolated accessory app's window. The attempt through a Finder binding and the subsequent unique-hotkey workaround also did not produce a QA window. These automation results do not establish a product menu-item or hotkey defect. The following checks remain **unperformed**, rather than passed:

- Enable/disable login registration, approval in System Settings, refresh on return, and signed installed-app logout/login or restart.
- AI insertion-point movement, modified arrows, single Return submission, layered Escape, hide/reopen focus, and restore-to-previous-app behavior.
- Recording cancellation, pinned calendar plus About, hidden-panel pass-through, and repeated monitor lifecycle cycles.
- Today versus another selected day, real permission changes, loading/error/retry display, and rapid selection under delayed queries.
- Diagnostics through About: the native save dialog and its cancel/save/overwrite behavior, Powerbox access in the signed sandboxed app, Desktop and another chosen location, destination write failure, and the retained Finder/export-again/retry actions.
- Open-panel performance after preferences/content resizing, sleep/wake, midnight, display changes, and days-long availability.

## Small-display and accessibility acceptance remains open

The first release retains a single unscrollable calendar/preferences VStack (`CalendarPopoverView.swift:29–52`) and the existing panel height cap/anchor (`CalendarPanel.swift:82–91`). It does not implement the audit's screen-fit proposal. A small or scaled display with preferences, AI, several events, and wrapped recovery/error text can still require a layout correction. Verify that every setting and the footer is reachable within the usable screen bounds before claiming small-display acceptance.

Only the launch-at-login control receives the new explicit name/status treatment. Existing empty-label Toggles/Pickers, icon-sized hit areas, AI clear naming, date-cell semantics, and the `.focusable(false)` policy remain to be assessed. The first release does not establish full keyboard accessibility, VoiceOver correctness, larger-text behavior, or improved touch/click target coverage.

Hotkey registration-conflict feedback and preserving the previous successfully registered shortcut remain deferred: the recorder still saves the proposed combination and registration failures are logged in `GlobalHotkey.swift`. Updater error retry is also outside this iteration. These original audit findings are not closed by lifecycle fixes or diagnostic Retry.

## Bound on the release claim

A supportable claim is: “This iteration reports macOS login status accurately, provides settings recovery, corrects selected-day event states, scopes calendar input handling, and makes diagnostics recoverable.”

Do not claim the other-machine crash reproduced or fixed, restart reliability verified, long-term disappearance resolved, all UX accepted, improved open-panel performance, or days-long uptime. The original report lacks a reproducer, and a minute of idle observation plus source/tests cannot supply those conclusions.

Final quality, artifact/release verification, and readiness remain the parent task's separate gates. The next native session should complete the interaction matrix above and collect signed installed-build startup and sustained runtime evidence before expanding the UX acceptance claim.
